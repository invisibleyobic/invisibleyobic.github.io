# Приём заказов ОЗОТЭНС

WSGI-приложение использует исходный order_core.py и прайс из 15 позиций. SQLite хранит заказы и уникальные ключи запросов. Ответ содержит номер, серверную сумму и статус pending_confirmation.

## Проверка

Python 3.9+ со стандартным модулем sqlite3. В папке сервера выполнить python -m unittest discover -s tests -v.

## Будущий хостинг в РФ

1. Поместить папку вне публичного каталога сайта.
2. Создать отдельного системного пользователя, дать доступ к базе и её резервным копиям только оператору сервиса.
3. Установить WSGI-сервер, например python -m pip install gunicorn.
4. Задать переменные из .env.example средствами хостинга. Само приложение этот файл не загружает.
5. Запустить за HTTPS-прокси под супервизором процессов командой gunicorn --workers 2 --bind 127.0.0.1:8000 --access-logfile /dev/null wsgi:application.

В прокси ограничить тело запроса 32 КБ и настроить таймаут чтения. Передавать реальный адрес клиента в WSGI REMOTE_ADDR доверенными средствами хостинга. Произвольному X-Forwarded-For приложение не доверяет. При неправильной настройке все клиенты прокси разделяют один лимит.

Настроить копирование SQLite, проверку восстановления, контроль доступа. Тела запросов и данные покупателя не помещать в журналы. CORS разрешает только точные значения OZOTENS_ALLOWED_ORIGINS без завершающего слеша.

## API

GET /health возвращает {"status":"ok"}. Публичного просмотра заказов нет.

POST /orders принимает JSON и заголовок Idempotency-Key из 16–64 латинских букв, цифр, дефисов и подчёркиваний.

Формат JSON

    {
      "items": [{"code": "85/04", "size": "M", "qty": 1}],
      "customer": {
        "name": "Имя покупателя", "phone": "+79001234567",
        "email": "", "city": "Город", "comment": "",
        "consents": {"personal_data": true, "offer": true, "marketing": false}
      },
      "delivery": {"method": "pickup", "address": "Адрес пункта выдачи"},
      "source": "unknown", "website": ""
    }

Доставка поддерживает pickup и courier, данные сохраняются отдельно. Старые клиенты могут передать customer.delivery и customer.address. Цены из запроса игнорируются.

Первый ответ имеет HTTP 201, идентичный повтор HTTP 200

    {"order_id": "идентификатор", "total": 31750, "status": "pending_confirmation"}

Ключ с другим заказом возвращает HTTP 409. Транзакция и уникальный индекс предотвращают дубли при параллельных запросах. Ключ и тело сохраняют для повторов после сетевого сбоя. Заказ остаётся в базе после перезапуска.

## Подключение сайта

Подготовить реквизиты продавца, оферту, политику и согласия. Проверить реальную доставку, контакты и обработку заказов оператором. В ozotens/commerce-catalog.json задать orders.enabled=true и orders.endpoint=https://адрес-api/orders.

Серверный catalog.json задаёт фактические суммы. Сверять его с витриной при обновлении прайса. Заказы в текущей сборке сайта выключены.

## Подключение оплаты

После выбора провайдера добавить серверное создание платёжной сессии по сохранённой серверной сумме и номеру заказа. Возвращать payment_url только после создания сессии. Проверять подпись вебхука по документации провайдера. Хранить номера событий с уникальным индексом, менять статус платежа в транзакции. Возврат браузера не подтверждает оплату.

В исходном order_core.py есть базовая функция HMAC. Формат нужно сопоставить с провайдером. Платежи потребуют отдельной миграции базы, обработки повторов, отмен и возвратов. Текущий API принимает заказ для подтверждения оператором.
